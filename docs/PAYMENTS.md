## 1. Как это устроено

```
 сайт / Mini App / бот
        │  startPayment(order, { channel, returnUrl })          src/payments/index.js
        ▼
 провайдер.createPayment() ── запись попытки в таблицу payments
        │
        ├─ redirectUrl  → покупатель уходит на страницу оплаты (mock, Payme, Click)
        └─ invoiceLink  → счёт Telegram (Mini App: openInvoice, сайт: страница «Оплата в Telegram»)

 платёжная система → наш сервер (callback / обновление бота / форма демо-страницы)
        │
        ▼
 orders.markPaid(orderId, { provider, txId, amount })           src/services/orders.js
   одна транзакция БД: заказ → «Оплачен», платёж → paid, списание остатков,
   активация/продление подписки, событие purchase, история;
   после фиксации — уведомления администраторам и покупателю.
```

Три правила, на которых держится модуль:

1. **Деньги меняют состояние только в одном месте.** Провайдеры сами заказы не трогают: успех —
   `orders.markPaid()`, отказ — `orders.markPaymentFailed()`, возврат — `orders.refund()`. Все три
   функции идемпотентны.
2. **Каждая попытка оплаты — строка в `payments`.** Она создаётся, когда покупателя отправляют к
   провайдеру, и дальше меняется callback-ами провайдера. В админке (*Заказы → заказ → Платежи*)
   видна вся история попыток.
3. **Возврат покупателя ничего не решает.** Параметры в адресе возврата не читаются вообще;
   состояние заказа берётся из базы, а в базу оно попадает только из проверенного callback-а.

Суммы в базе — целые сумы. Тийины (× 100) появляются только на границе с Payme и Telegram.
Валюта — `UZS`.

### Таблица `payments`

| Поле | Смысл |
|---|---|
| `provider` | `mock`, `telegram`, `payme`, `click`, `manual` (отметка «оплачен» из админки) |
| `provider_tx_id` | номер транзакции у провайдера (Payme `id`, Click `click_trans_id`, Telegram `telegram_payment_charge_id`); пусто, пока провайдер не подхватил попытку |
| `amount` | сумма в сумах |
| `status` | `created` (покупатель отправлен к провайдеру) → `pending` (провайдер открыл транзакцию) → `paid` / `cancelled` / `failed` / `refunded` |
| `state`, `reason` | состояние и причина отмены Payme (`1`, `2`, `-1`, `-2`; причины `1…5`, `10`) |
| `create_time`, `perform_time`, `cancel_time` | время в миллисекундах |
| `error` | текст последней ошибки или причина закрытия |
| `raw` | JSON: адрес возврата покупателя, канал, служебные данные провайдера |

## 2. Выбор провайдера

Активный провайдер — настройка **Админка → Настройки → Оплата → «Платёжный провайдер»**; если она
пустая, берётся переменная `PAYMENT_PROVIDER` (`mock`, `telegram`, `payme`, `click`).

Каждый провайдер сам сообщает, готов ли он (`isConfigured()`):

| Провайдер | Считается настроенным, когда заданы |
|---|---|
| `mock` | ничего не нужно; в production — только при `ALLOW_MOCK_PAYMENTS=1` |
| `telegram` | `BOT_TOKEN` и `TELEGRAM_PAYMENT_TOKEN` |
| `payme` | `PAYME_MERCHANT_ID` и `PAYME_KEY` |
| `click` | `CLICK_SERVICE_ID`, `CLICK_MERCHANT_ID`, `CLICK_SECRET_KEY` |

Если выбран ненастроенный провайдер:

- **вне production** оплата идёт через демо-страницу (удобно на стенде);
- **в production** покупатель видит «Онлайн-оплата временно недоступна» (HTTP 503), заказ остаётся
  неоплаченным. Товар «бесплатно» не уходит никогда.

Mini App сначала пробует счёт Telegram (если настроен), иначе — страницу активного провайдера.
Callback-и Payme и Click принимаются всегда, когда заданы их ключи, — независимо от того, какой
провайдер активен: покупатель может оплатить заказ и из приложения Payme/Click по номеру заказа.

После смены переменных окружения перезапустите приложение. Настройка в админке применяется сразу.

## 3. Адреса `/pay/*`

| Адрес | Кто вызывает | Что делает |
|---|---|---|
| `GET /pay/order/<token>[?return=/путь]` | покупатель (кнопка «Оплатить») | начинает оплату активным провайдером и перенаправляет на его страницу |
| `GET /pay/return/<token>` | Payme, Click (адрес возврата) | читает состояние из базы; если callback ещё в пути — показывает страницу ожидания |
| `GET /pay/status/<token>` | страницы ожидания (JS) | JSON: `{ ok, number, status, payment_status, paid, can_pay }` |
| `GET /pay/invoice/<token>` | покупатель на сайте | страница «Оплата в Telegram» со ссылкой на счёт |
| `GET/POST /pay/mock/<tx>` | покупатель | демо-страница оплаты |
| `POST /pay/payme` | серверы Payme | Merchant API (JSON-RPC 2.0, Basic-авторизация) |
| `POST /pay/click/prepare`, `POST /pay/click/complete` | серверы Click | SHOP API (form-urlencoded, подпись md5) |

`<token>` — случайный `public_token` заказа (его нельзя подобрать). `/pay/payme` и `/pay/click/*`
не используют cookie и CSRF: каждый запрос проверяется по ключу или подписи, а ответ всегда приходит
с HTTP 200 в формате провайдера — даже на мусорный запрос.

Платёжным системам нужен публичный адрес с HTTPS: `BASE_URL=https://ваш-домен`.

## 4. Демо-оплата (`mock`)

Встроенная страница `/pay/mock/<tx>`: состав заказа, «тестовая карта» и три кнопки —
**«Оплатить»** (успех), **«Отклонить»** (отказ банка), **«Вернуться в магазин»** (ничего не меняет).
Форма защищена CSRF-токеном, попытку можно использовать один раз, повторная отправка ничего не меняет.

- Ничего настраивать не нужно: это провайдер по умолчанию для демонстраций и тестов.
- **В production выключена.** При `NODE_ENV=production` провайдер считается ненастроенным, страницы
  `/pay/mock/*` отвечают 404. Чтобы показать демо на «боевой» сборке, задайте
  `ALLOW_MOCK_PAYMENTS=1` — осознанно: с этим флагом заказ можно «оплатить» без денег.
- Проверка: оформите заказ на сайте → «Оплатить» → на демо-странице нажмите «Отклонить»: заказ
  получит статус оплаты «Ошибка оплаты» и кнопку «Попробовать ещё раз»; затем «Оплатить» — заказ станет оплаченным.

## 5. Telegram Payments (`telegram`)

Оплата картой прямо в Telegram. Деньги принимает платёжная система, подключённая к боту
(Click, Payme и др.), — магазин получает только уведомление.

### Настройка

1. В [@BotFather](https://t.me/BotFather): `/mybots` → ваш бот → **Payments** → выберите платёжную
   систему и пройдите её подключение. Для проверки возьмите тестовый режим — в токене будет `:TEST:`.
2. Скопируйте выданный токен в `.env`:
   ```
   BOT_TOKEN=123456:AA...
   TELEGRAM_PAYMENT_TOKEN=398062629:TEST:...
   # 1 — форма счёта попросит у покупателя номер телефона
   TELEGRAM_PAYMENT_NEED_PHONE=0
   ```
3. Перезапустите приложение. В админке (*Настройки → Оплата*) Telegram Payments станет «готов».
   Чтобы и сайт принимал оплату через Telegram, выберите его активным провайдером.

Регистрировать адреса нигде не нужно: Telegram сообщает об оплате самому боту.

### Как проходит платёж

| Шаг | Где |
|---|---|
| счёт: `title` «Заказ SC-…», `description` — состав, `payload` = `order:<id заказа>`, `currency` = `UZS`, `prices` — позиции заказа в тийинах (сумма строк = сумма заказа × 100) | `buildInvoiceParams(order)` в `src/payments/providers/telegram.js` |
| Mini App: ссылка `createInvoiceLink` → `Telegram.WebApp.openInvoice(link)` | `startPayment(order, { providerId: 'telegram' })` |
| сайт: `/pay/order/<token>` → страница `/pay/invoice/<token>` с кнопкой «Открыть счёт в Telegram»; страница сама заметит оплату | `src/payments/routes.js` |
| бот: `sendInvoice` с теми же параметрами | `src/bot/handlers/payments.js` |
| `pre_checkout_query`: заказ существует, не оплачен, не отменён, сумма и валюта совпадают | `telegramPayments.validatePreCheckout()` |
| `successful_payment` → `orders.markPaid(…, { provider: 'telegram', txId: telegram_payment_charge_id })` | `telegramPayments.handleSuccessfulPayment()` |

Ссылку на счёт можно открыть много раз, поэтому заказ проверяется заново в `pre_checkout_query`:
оплаченный или отменённый заказ Telegram оплатить не даст; для товарных заказов там же проверяются
остатки на складе.

**Повторное списание.** Повторная доставка того же `successful_payment` (тот же
`telegram_payment_charge_id`) ничего не меняет. Если же по уже оплаченному заказу приходит платёж с
**другим** `telegram_payment_charge_id` — это настоящее второе списание (заказ успели оплатить иначе
между `pre_checkout_query` и `successful_payment`, либо один счёт оплатили с двух устройств).
Такой платёж записывается отдельной строкой `payments` со статусом «Ошибка» и пояснением, в историю
заказа добавляется заметка, администраторы получают сообщение «второе списание… нужен возврат»,
покупатель — что лишнее списание вернут. Деньги возвращаются в кабинете платёжной системы.

Если Telegram не создал счёт (неверный токен, сумма вне допустимого диапазона), попытка
записывается со статусом «Ошибка», а Mini App предлагает страницу оплаты активного провайдера.
У Telegram есть минимальная и максимальная сумма счёта для каждой валюты (ориентир — эквивалент
1 и 10 000 USD); актуальные значения — в документации Bot API.

### Проверка

С тестовым токеном оплатите заказ тестовой картой платёжной системы (номера карт — в её
документации). Автотесты (`tests/payments.telegram.test.js`, `tests/bot.payments.test.js`) работают
с поддельным сервером Bot API: адрес API задаётся переменной `TELEGRAM_API_ROOT`.

## 6. Payme Business (`payme`)

Покупатель платит на странице Payme, а Payme общается с магазином по Merchant API.
Документация Payme: <https://developer.help.paycom.uz>.

### Настройка в кабинете Payme Business

1. Создайте кассу (веб-касса) в кабинете мерчанта.
2. В настройках кассы:
   - **Endpoint URL** — `https://ваш-домен/pay/payme`;
   - **реквизиты платежа (account)** — одно поле с именем `order_id` (обязательное).
     Если поле названо иначе, укажите его имя в `PAYME_ACCOUNT_FIELD`.
3. Скопируйте **ID кассы** и **ключ** (сначала тестовый) в `.env`:
   ```
   PAYMENT_PROVIDER=payme
   PAYME_MERCHANT_ID=5e730e8e0b852a417aa49ceb
   PAYME_KEY=<тестовый ключ>
   PAYME_TEST=1            # 1 — песочница, 0 — боевой режим
   PAYME_ACCOUNT_FIELD=order_id
   ```
4. Для боевого режима замените ключ на боевой и поставьте `PAYME_TEST=0`.

### Страница оплаты

```
https://checkout.paycom.uz/<base64( m=<PAYME_MERCHANT_ID>;ac.order_id=<id заказа>;a=<сумма в тийинах>;c=<адрес возврата> )>
```

При `PAYME_TEST=1` используется `https://checkout.test.paycom.uz`. Адрес возврата — всегда
`{BASE_URL}/pay/return/<token>` (см. [раздел 8](#8-возврат-покупателя-в-магазин)).
В поле `order_id` передаётся внутренний номер заказа (`orders.id`); callback-и принимают и
«человеческий» номер `SC-100042`, чтобы заказ можно было оплатить из приложения Payme.

### Merchant API

`POST /pay/payme`, тело — JSON-RPC 2.0, заголовок `Authorization: Basic base64("Paycom:<PAYME_KEY>")`.
Ключ сравнивается за постоянное время. Ответ всегда HTTP 200; ошибка — объект
`error: { code, message: { ru, uz, en }, data }`.

| Метод | Что делает магазин |
|---|---|
| `CheckPerformTransaction` | проверяет заказ и сумму → `{ allow: true, additional: { order } }` |
| `CreateTransaction` | создаёт транзакцию (состояние `1`), заказ → «Ожидает оплаты». Повтор с тем же `id` возвращает тот же ответ |
| `PerformTransaction` | `orders.markPaid()` и состояние `2` — в одной транзакции БД. Повтор возвращает тот же `perform_time` |
| `CancelTransaction` | из `1` → `-1`: заказ снова можно оплатить. Из `2` → `-2`: `orders.refund()` (возврат остатков, откат подписки). Транзакция, которая уже оплатила заказ, считается проведённой, даже если состояние `2` не успело сохраниться: её отмена — тоже возврат (`-2`), а не простая отмена. Повтор возвращает тот же ответ |
| `CheckTransaction` | `create_time`, `perform_time`, `cancel_time`, `transaction`, `state`, `reason` |
| `GetStatement` | транзакции за период `from…to` (по времени создания в Payme), по возрастанию |

Состояния: `1` создана · `2` проведена · `-1` отменена до проведения · `-2` отменена после проведения.

| Код | Когда |
|---|---|
| `-32504` | нет или неверная Basic-авторизация |
| `-32700` | тело запроса — не JSON |
| `-32600` | нет обязательных полей или неверный тип (`id`, `time`, `amount`, `account`, `reason`, `from`, `to`) |
| `-32601` | неизвестный метод |
| `-32300` | запрос не методом POST |
| `-32400` | внутренняя ошибка магазина |
| `-31001` | сумма не равна сумме заказа (в тийинах) |
| `-31050` | заказ не найден (`data` = имя поля счёта) |
| `-31051` | заказ уже оплачен |
| `-31052` | заказ отменён или возвращён |
| `-31053` | товар из заказа закончился на складе (остатки неоплаченными заказами не резервируются) |
| `-31099` | по заказу уже есть транзакция в состоянии `1` (на заказ — одна активная транзакция) |
| `-31003` | транзакция не найдена |
| `-31008` | операцию выполнить нельзя: транзакция отменена, истёк срок, заказ оплачен другим способом или отменён, товар закончился после `CreateTransaction` |
| `-31007` | отменить нельзя: заказ уже передан курьеру или доставлен |

Важные детали:

- **Тайм-аут 12 часов.** Транзакция, которая провела в состоянии `1` больше 12 часов, отменяется с
  причиной `4`; `PerformTransaction` по ней получает `-31008`, заказ освобождается для новой попытки.
- **Заказ оплачен другим способом**, пока транзакция Payme ждала (Click, Telegram, отметка
  менеджера): `PerformTransaction` получает `-31008`, транзакция отменяется с причиной `3` — Payme
  возвращает деньги покупателю, двойной оплаты нет.
- **Отмена после проведения** разрешена, пока заказ в статусах «Оплачен» и «Собирается». Для заказов
  «Передан курьеру» и «Доставлен» Payme получает `-31007` — такие возвраты оформляются вручную.
- **Остатки.** `CheckPerformTransaction` и `CreateTransaction` отвечают `-31053`, если товара из
  заказа уже нет на складе; если он закончился, пока транзакция ждала, `PerformTransaction` получает
  `-31008`, транзакция отменяется с причиной `3`, заказ остаётся доступным для оплаты позже.

### Проверка

1. В песочнице Payme (<https://test.paycom.uz>) укажите ID кассы и тестовый ключ, затем пройдите
   сценарии: неверная авторизация, неверная сумма, несуществующий счёт, создание, проведение и
   отмена транзакции. Номер счёта для сценариев — `id` неоплаченного заказа (он есть в адресе
   заказа в админке).
2. Оплатите заказ с сайта тестовой картой из документации Payme.
3. Или вручную:
   ```bash
   AUTH=$(printf 'Paycom:%s' "$PAYME_KEY" | base64 -w0)
   curl -s https://ваш-домен/pay/payme -H "Authorization: Basic $AUTH" -H 'Content-Type: application/json' \
     -d '{"jsonrpc":"2.0","id":1,"method":"CheckPerformTransaction","params":{"amount":12900000,"account":{"order_id":"42"}}}'
   ```

Автотесты: `tests/payments.payme.test.js` (полный жизненный цикл и все коды ошибок).

## 7. Click SHOP API (`click`)

Покупатель платит на странице Click, Click дважды обращается к магазину: **Prepare** (можно ли
принять платёж) и **Complete** (платёж прошёл или отменён). Документация: <https://docs.click.uz>.

### Настройка в кабинете Click

1. В кабинете мерчанта создайте сервис (SHOP API) и укажите адреса:
   - **Prepare URL** — `https://ваш-домен/pay/click/prepare`
   - **Complete URL** — `https://ваш-домен/pay/click/complete`
2. Перенесите параметры сервиса в `.env`:
   ```
   PAYMENT_PROVIDER=click
   CLICK_SERVICE_ID=12345
   CLICK_MERCHANT_ID=6789
   CLICK_SECRET_KEY=<secret key>
   CLICK_MERCHANT_USER_ID=1234      # необязательно: добавляется в ссылку на оплату
   ```

### Страница оплаты

```
https://my.click.uz/services/pay?service_id=<…>&merchant_id=<…>&amount=<сумма N.NN>&transaction_param=<id заказа>&return_url=<адрес возврата>
```

### Callback-и

Запросы приходят как `application/x-www-form-urlencoded`, ответ — JSON, всегда HTTP 200.

```
Prepare  (action=0): sign_string = md5(click_trans_id + service_id + SECRET_KEY + merchant_trans_id + amount + action + sign_time)
Complete (action=1): sign_string = md5(click_trans_id + service_id + SECRET_KEY + merchant_trans_id + merchant_prepare_id + amount + action + sign_time)
```

`merchant_trans_id` — номер заказа (`orders.id`; принимается и `SC-100042`).
`merchant_prepare_id` и `merchant_confirm_id` — номер строки в `payments`. Подпись сравнивается за
постоянное время, значения берутся ровно в том виде, в каком пришли.

| `error` | `error_note` | Когда |
|---|---|---|
| `0` | Success | запрос принят |
| `-1` | SIGN CHECK FAILED! | подпись не сошлась (или Click не настроен) |
| `-2` | Incorrect parameter amount | сумма не равна сумме заказа |
| `-3` | Action not found | `action` не соответствует адресу (Prepare — `0`, Complete — `1`) |
| `-4` | Already paid | Prepare: заказ уже оплачен (деньги ещё не списаны). Complete: **эта же** транзакция уже подтверждена — повторный Complete после потерянного ответа; платёж остаётся в силе |
| `-5` | User does not exist | заказ не найден |
| `-6` | Transaction does not exist | `merchant_prepare_id` не найден или относится к другому заказу / другой транзакции Click |
| `-7` | Failed to update user | внутренняя ошибка магазина |
| `-8` | Error in request from click | не хватает обязательных полей, чужой `service_id`, испорченное тело запроса |
| `-9` | Transaction cancelled | заказ отменён, транзакция уже отменена, товар закончился на складе, либо заказ уже оплачен **другим** платежом (Complete) |

- Повторный **Prepare** с тем же `click_trans_id` возвращает тот же `merchant_prepare_id`.
- **Complete с `error < 0`** (Click не смог списать деньги): транзакция отменяется, заказ получает
  статус оплаты «Ошибка оплаты» и остаётся доступным для новой попытки; ответ — `-9`.
- Если заказ успели оплатить иначе (вторая транзакция Click, Payme, Telegram, отметка менеджера),
  Complete получает **`-9`**: транзакция отменяется, Click возвращает деньги покупателю. Код `-4`
  здесь не используется — он означал бы «эта транзакция подтверждена», и второе списание осталось бы
  у магазина. Если Click сообщил, что деньги списаны (`error = 0`), администраторы получают
  сообщение «Click: второе списание по уже оплаченному заказу» — проверьте в кабинете, что возврат прошёл.
- **Остатки.** Неоплаченные заказы товар не резервируют: Prepare отвечает `-9`, если товара уже нет;
  если он закончился между Prepare и Complete — Complete тоже `-9` (Click возвращает деньги).

### Проверка

запросы). Вручную callback можно собрать так:

## 8. Возврат покупателя в магазин

Payme и Click получают один и тот же адрес возврата — `{BASE_URL}/pay/return/<token>`. Обработчик:

1. находит заказ по токену и **не читает ни одного параметра из адреса** (их может дописать кто угодно);
2. если заказ уже оплачен или оплату никто не начинал — сразу отправляет покупателя на страницу, с
   которой тот пришёл (она сохранена в попытке оплаты: страница заказа на сайте или экран Mini App);
3. если у провайдера есть открытая транзакция, а подтверждение ещё не пришло, — показывает страницу
   «Проверяем оплату»: она каждые несколько секунд спрашивает `/pay/status/<token>` и сама переходит
   дальше, когда заказ оплачен.

Адрес, на который возвращается покупатель (`returnUrl`), проверяется: допустимы только пути этого
сайта (`/tma/#/pay/5`) и адреса под `BASE_URL`; всё остальное заменяется страницей заказа.

## 9. Один заказ — одна оплата

- `orders.markPaid()` идемпотентна: повторный вызов для оплаченного заказа ничего не меняет
  (остатки, подписка, событие `purchase`, уведомления — один раз).
- Повторные callback-и одной транзакции получают тот же ответ, что и первый (Payme) или
  «Already paid» `-4` (Click, только для транзакции, которая оплатила заказ).
- Когда заказ оплачен, все остальные открытые попытки закрываются. Транзакции других провайдеров,
  которые были «в пути», получают отказ (`-31008` у Payme, `-9` у Click, отказ в
  `pre_checkout_query` у Telegram) — провайдер возвращает покупателю деньги.
- Списание, которое всё же прошло по уже оплаченному заказу (Complete от Click с `error = 0`,
  `successful_payment` от Telegram с новым `telegram_payment_charge_id`), не считается повтором:
  оно фиксируется в `payments` / истории заказа, и администраторы получают сообщение — эти деньги
  нужно вернуть.
- **Остатки не резервируются** неоплаченными заказами, поэтому каждый путь оплаты проверяет склад
  прямо перед списанием: `startPayment()` (ошибка `out_of_stock`), `pre_checkout_query` Telegram,
  Payme (`-31053` / `-31008`), Click (`-9`), демо-страница. Если оплата всё-таки прошла при нехватке
  (например, «Отметить оплаченным» в админке), со склада списывается только то, что было, это
  записывается в заказ (`order_items.stock_taken`), а администраторы получают предупреждение.
- Сумма проверяется на каждом шаге и у каждого провайдера; несовпадение — отказ.
- `startPayment()` не верит переданному объекту заказа: перечитывает его из базы, проверяет, что
  заказ можно оплатить и что сумма — положительное целое число сумов.

Эти правила проверяет `tests/payments.cross.test.js`: на один заказ открываются попытки во всех
четырёх провайдерах, один платит первым, остальные получают отказ.

## 10. Возврат денег

| Провайдер | Как вернуть деньги |
|---|---|
| Payme | возврат в кабинете Payme → Payme вызывает `CancelTransaction` → заказ сам переходит в «Возврат» (пока он не передан курьеру). Для переданных и доставленных заказов Payme получит `-31007` |
| Click, Telegram | верните деньги в кабинете платёжной системы, затем в админке переведите заказ в статус «Возврат» |
| демо | в админке переведите заказ в статус «Возврат» |

Статус «Возврат» в админке (`orders.refund()`) возвращает на склад ровно то количество, которое было
списано при оплате, откатывает период подписки, оплаченный **именно этим** заказом (см. раздел 11),
и уведомляет покупателя, но **сам деньги не переводит** — это делает платёжная система.

## 11. Подписки: как продлеваются

Подписка — это **предоплаченные периоды**, автоматического списания с карты нет.

1. Покупатель выбирает план → создаётся заказ вида «Подписка» → оплата любым провайдером.
2. Оплата (`orders.markPaid`) активирует подписку на `period_days` дней. Если у покупателя уже есть
   активная подписка на тот же план, период **продлевается** от даты её окончания.
3. За 3 дня до конца периода бот напоминает покупателю и предлагает кнопку «Продлить»: она создаёт
   новый заказ и счёт. После окончания периода бот сообщает, что подписка закончилась.
   Напоминания приходят тем, у кого подписка привязана к Telegram, и только в дневные часы.
4. Неоплаченная вовремя подписка получает статус «Истекла» (проверка раз в час); покупатель может
   оформить её заново в любой момент.
5. Каждый оплаченный заказ подписки записывается как отдельный период (таблица
   `subscription_periods`: заказ → подписка → число дней). Возврат **любого** заказа — первого,
   промежуточного или последнего — убирает ровно его период. Когда оплаченных периодов не осталось,
   подписка отменяется. Если возвращённый заказ был переходом на другой план (он отменял прежнюю
   подписку), прежняя подписка восстанавливается, пока её оплаченный срок не истёк.

Почему так: автосписание требует привязки карты (токенизации) и отдельного договора с Payme / Click
на рекуррентные платежи. Модель «предоплата + напоминание» работает с любым провайдером и не хранит
платёжные данные покупателей. При необходимости автосписание добавляется отдельным провайдером:
его задача — по расписанию создавать заказ-продление и вызывать `orders.markPaid()` после списания.

## 12. Журнал платежей

Каждый callback и каждое начало оплаты пишется в stdout одной строкой JSON:

```json
{"ts":"2026-03-01T07:30:45.120Z","scope":"payments","event":"payme.rpc","method":"PerformTransaction","rpc_id":17,"tx":"65f1c0…","ok":true,"state":2,"ms":4}
{"ts":"2026-03-01T07:31:02.004Z","scope":"payments","event":"click.complete","click_trans_id":7000001,"order":"42","amount":"129000","confirm_id":311,"error":0,"ms":3}
{"ts":"2026-03-01T07:31:40.511Z","scope":"payments","event":"start","provider":"payme","order":43,"number":"SC-100043","amount":129000,"currency":"UZS","channel":"site"}
```

События: `start`, `start_failed`, `payme.rpc`, `payme.rejected`, `payme.release_failed`,
`click.prepare`, `click.complete`, `click.rejected`, `mock.result`. Ключи, заголовок авторизации, подписи и токены в журнал не попадают:
поля с такими именами заменяются на `[redacted]` (`src/payments/log.js`).

## 13. Как добавить провайдера

1. Создайте `src/payments/providers/<id>.js` с объектом по умолчанию:
   ```js
   export default {
     id: 'uzum',
     title: 'Uzum Bank',
     isConfigured: () => Boolean(config.payments.uzum?.merchantId),
     async createPayment(order, ctx) {            // ctx: { returnUrl, channel, tgUserId }
       recordAttempt(order, 'uzum', { raw: { returnUrl: ctx.returnUrl, channel: ctx.channel } });
       return { redirectUrl: buildCheckoutUrl(order, providerReturnUrl(order)) };
     },
   };
   ```
   Помощники — в `src/payments/common.js`: `recordAttempt`, `findOpenAttempt`, `findOrderByRef`,
   `providerReturnUrl`, `safeEqual`, `isChargeable`.
2. Зарегистрируйте его в `src/payments/index.js`: `registerProvider(uzum)`.
3. Callback провайдера добавьте в `src/payments/routes.js`. В обработчике:
   проверьте подпись/ключ (`safeEqual`), найдите заказ, сверьте сумму, затем вызовите
   `orders.markPaid()` / `orders.markPaymentFailed()` / `orders.refund()`; отвечайте в формате
   провайдера и записывайте событие через `paymentLog()`.
4. Адрес callback-а добавьте в `CSRF_IGNORE` и `COOKIELESS` в `src/app.js` (у провайдера нет
   нашего CSRF-токена), домен страницы оплаты — в `formAction` политики CSP там же.
5. Переменные окружения — в `src/config.js` и `.env.example`; пункт в списке провайдеров — в
   `SETTINGS_SCHEMA` (`src/services/settings.js`) и в `oneOf('PAYMENT_PROVIDER', …)`.
6. Тесты — `tests/payments.<id>.test.js`: успех, неверная подпись, неверная сумма, повторы,
   отмена и обязательно сценарий «заказ уже оплачен другим провайдером».

## 14. Чек-лист перед запуском

- [ ] `NODE_ENV=production`, `BASE_URL=https://…`, сайт доступен из интернета по HTTPS.
- [ ] `ALLOW_MOCK_PAYMENTS` не задан (или `0`).
- [ ] Боевые ключи: `PAYME_KEY` + `PAYME_TEST=0`; `CLICK_SECRET_KEY`; боевой `TELEGRAM_PAYMENT_TOKEN` (без `:TEST:`).
- [ ] В кабинетах зарегистрированы адреса: Payme — `/pay/payme`, Click — `/pay/click/prepare` и `/pay/click/complete`.
- [ ] В админке (*Настройки → Оплата*) выбран нужный провайдер и он отмечен как готовый.
- [ ] Пройдены сценарии песочницы Payme / проверка Click; сделана одна реальная оплата и один возврат.
- [ ] Журнал приложения собирается (stdout) — по нему разбираются спорные платежи.
- [ ] По возможности доступ к `/pay/payme` и `/pay/click/*` ограничен на прокси адресами платёжных
      систем (актуальные списки — в их документации).

## 15. Ограничения

- Автосписаний по подписке нет ([раздел 11](#11-подписки-как-продлеваются)).
- Фискальные данные чека (`detail` с кодами ИКПУ в ответе `CheckPerformTransaction`) не передаются:
  в каталоге нет кодов ИКПУ. Если касса Payme требует фискализацию, эти поля нужно добавить к товарам.
- Возврат денег для Click и Telegram выполняется в кабинете платёжной системы; магазин меняет только
  свой статус заказа.
- Реальные серверы Payme, Click и Telegram из среды разработки недоступны: протоколы проверены
  автотестами по документации и на поддельном сервере Bot API. Перед запуском обязательно пройдите
  песочницы платёжных систем.
- Счёт, отправленный ботом (`sendInvoice`), не создаёт строку попытки в `payments` — строка
  появляется при успешной оплате.
